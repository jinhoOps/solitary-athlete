# 묵묵 계정 연결 · 승인과 집계 설계

작성일: 2026-10-21

상태: 설계 검토본. 구현·마이그레이션·실서비스 적용 전.

현재 구현 기준: main `5fcadd6`.

## 1. 목적과 결정

여러 Discord 계정으로 운동을 인증하는 한 사람이 하나의 잔디와 통계로 기록을 돌아보게 한다. 사용자 접점은 묵묵봇이며, 두 계정에서 동의를 확인한 뒤 관리자가 검토·승인한다. 원본 인증의 작성자·메시지 ID는 유지한다.

사용자가 선택한 통계 정책은 **현재 기록을 사람 단위로 정확히 합산하고, 과거 관측값은 보존하며, 연결 전후 기준이 다른 표본의 증감 비교를 중단**하는 것이다. 통계 수치를 무조건 고정한다는 뜻은 아니다. 연결로 중복 인원과 운동일이 제거되는 결과는 정상 반영한다.

| 검토한 방법 | 장점 | 판단 |
| --- | --- | --- |
| 승인 후 다음 성공 수집에서 전체 조회·집계를 함께 전환 | 중복을 정확히 제거하고 개인·전체가 같은 기준을 사용 | 채택 |
| 다음 달부터 사람 단위 집계 | 월중 전환을 피함 | 연간 잔디·개인 기록은 계속 불일치하므로 제외 |
| 개인 잔디만 합치고 전체는 계정별 집계 | 기존 전체 수치 유지 | 참여 인원과 중복 운동일이 실제 사람 수와 달라지므로 제외 |

첫 버전은 한 서버, 기존 사람에 별도 계정 하나씩 연결, 개별 보조 계정 해제까지 다룬다. 이미 여러 계정이 묶인 두 그룹의 병합, 대표 계정 교체, 접근 불가능한 계정의 동의 면제, 자동 계정 추정은 제공하지 않는다. 실제 사용자 ID는 예시·테스트·문서에 넣지 않는다.

## 2. 사용자 명령과 확인 화면

두 최상위 명령으로 일반 사용과 관리자 검토를 분리한다. 기존 수신기는 명령 interaction만 처리하므로 계정 기능에서 사용할 명령(type 2), 버튼(type 3), 거절 사유 모달 제출(type 5)을 명시적으로 분기한다. 서명·서버·앱 검사는 모든 분기 앞에서 공통으로 수행한다. 명령명·설명·안내 문구는 한국어로 작성한다.

| 명령 | 사용자와 동작 |
| --- | --- |
| `/계정연결 신청 유저:@계정` | 대표로 사용할 계정에서 실행. 상대 계정 연결을 신청하고 본인 동의를 기록 |
| `/계정연결 현황` | 본인이 관련된 요청과 현재 연결된 계정, 대표 계정, 승인·적용 상태 조회 |
| `/계정연결 취소 요청:번호` | 승인 전 요청을 어느 당사자든 취소 |
| `/계정연결 해제 유저:@계정` | 본인 그룹의 보조 계정 하나를 해제 요청. 대표 계정은 해제 대상이 될 수 없음 |
| `/계정검토 목록` | 관리자에게 검토 대기와 승인 후 반영 대기·처리 오류를 페이지 단위로 표시 |
| `/계정검토 상세 요청:번호` | 당사자, 동의 시각, 원본 보존 안내, 현재 집계에 미치는 영향을 표시 |

`/계정연결 현황`의 상대 계정 화면에 `동의`·`거절` 버튼을 제공한다. 공유된 요청 번호만으로 동의할 수 없고, 서버가 서명된 interaction의 실제 호출자와 요청의 상대 계정 ID를 대조한다. 링크나 확인 코드를 다른 사람이 전달받아도 권한이 생기지 않는다. 상대 계정이 직접 명령을 호출하므로 DM·공개 초대 메시지·상시 Gateway 연결은 필요하지 않다. 사용자가 상대 계정으로 로그인해 확인하도록 첫 응답에서 안내한다.

관리자 상세에는 `영향 다시 확인`·`승인`·`거절` 버튼을 제공한다. 거절에는 1~200자의 사유를 받는다. 승인 확인 화면에는 대표 계정, 연결/해제할 계정, 현재 월의 인원·칸 수·비율 및 전체 잔디 분모의 변경 예상치를 함께 보여준다. 부계정 원문 메모나 사진은 검토 화면에 가져오지 않는다.

모든 계정 관련 명령·버튼 응답은 호출자에게만 보이며 기존 응답 예약·300초 삭제를 재사용한다. 진행 상태는 DB에 남고, 안내가 사라져도 다시 명령으로 조회할 수 있다. 승인 결과를 오래된 interaction token으로 나중에 보내거나 자동 DM하지 않는다.

표현 예:

- `상대 계정에서도 /계정연결 현황으로 동의해 주세요.`
- `두 계정의 동의를 확인했어요. 관리자 검토를 기다리고 있어요.`
- `승인됐어요. 다음 성공 수집에서 기록과 통계에 함께 반영해요.`
- `계정 연결로 집계 기준이 바뀌어 전일 비교를 쉬어요.`

기록 없는 계정도 신청·동의할 수 있다. 연결만으로 운동 인원에 추가하지 않는다. 닉네임 변경은 같은 Discord ID로 계속 처리하며, 연결이나 관리 승인을 요구하지 않는다.

## 3. 권한·동의·요청 수명

일반 사용은 현재 서버의 `회원님` 역할 ID 보유자 또는 관리 권한 보유자에게 허용한다. 검토 권한은 기존 `/기록갱신`과 같은 `MANAGE_GUILD` 또는 `ADMINISTRATOR`로 판단한다. 역할 이름이나 버튼 표시 여부를 권한 근거로 쓰지 않는다. 봇에게 관리자 권한을 추가하지 않는다.

사용자가 선택한 승인 정책은 **다른 관리자 승인 필수**다. 요청의 대표·보조 계정 또는 그 계정과 이미 같은 사람으로 연결된 관리자는 자기 요청을 승인·거절할 수 없다. 두 계정 모두 관리자여도 별도의 관리자가 검토한다. 조건에 맞는 승인자가 없으면 반영 대기로 우회하지 않고 검토 대기로 남긴다. 관리자가 동의를 대신하거나 자기 승인 예외를 여는 기능은 제공하지 않는다.

일반 명령과 별도로 `/계정검토`의 기본 권한을 `MANAGE_GUILD`로 등록하되, 실제 처리 시에도 서버·앱·호출자·권한을 검사한다. 다른 서버·DM·봇·자기 자신 연결은 거부한다. 서명 검증을 거친 명령과 버튼 interaction만 접수한다. `custom_id`에는 작업 종류·불투명 요청 ID·버전을 넣되 신뢰하지 않고 DB의 대상·상태·버전을 다시 검사한다.

연결 신청은 대표 계정에서만 가능하다. 연결된 보조 계정으로 신청하면 대표 계정에서 진행하도록 안내한다. 대상은 아직 다른 다중 계정 그룹에 속하지 않은 계정이어야 한다. 그룹끼리 이어 붙이거나 A→B→C 식 참조를 만들지 않는다.

신청 시 호출자 동의, 상대 계정에서의 명시적 동의가 모두 필요하다. 요청의 계정·동작 내용은 생성 후 고정한다. 동의 대상인 내용 버전과 동시 처리 제어용 상태 버전을 구분하고, 정상적인 동의→검토 상태 전이로 기존 동의를 무효화하지 않는다. 동의는 해당 두 계정·대표 계정·동작·요청 내용 버전에만 유효하다. 그룹 구성 변경 시 기존 동의로 다른 구성에 적용하지 않는다. 로그인할 수 없는 계정은 관리자 단독 승인으로 우회하지 않고 이번 버전에서 처리하지 않는다.

승인·적용 직전에는 당사자의 현재 서버 가입·회원 자격과 승인자의 현재 관리 권한을 REST로 재확인한다. 조회 오류·429·5xx·타임아웃을 탈퇴나 동의 철회로 간주하지 않는다. 일시 오류는 보류하고, 확정된 자격 상실 또는 대상 구성 변경은 `invalidated`로 종료하고 재신청을 안내한다. 승인자와 당사자의 동일인 여부는 Discord ID 하나가 아니라 현재 연결 그룹까지 기준으로 판단한다.

동의 대기·검토 대기는 신청 후 7일에 만료한다. 승인된 요청은 수집기가 쉬는 동안 반영 대기로 유지하며 이 7일 만료를 적용하지 않는다. 만료 여부는 명령·버튼·작업 선점 시 검사하므로 새 Cron이 필요하지 않다. 같은 계정에 걸린 진행 중 변경 요청은 최대 1개이며, 동일 interaction 재전송·같은 요청 재호출은 기존 상태를 반환한다. 대상 계정은 원하지 않는 요청을 거절할 수 있다.

## 4. 상태와 승인 내용의 유효성

| 상태 | 다음 동작 |
| --- | --- |
| `awaiting_consent` 동의 대기 | 상대 계정 동의 시 `pending_review`; 거절·취소·만료 가능 |
| `pending_review` 검토 대기 | 관리자 확인 후 `approved`; 거절·당사자 취소·만료 가능 |
| `approved` 반영 대기 | 수집기에서 재검증·트랜잭션 성공 후 `applied` |
| `applied` 반영 완료 | 직접 되돌려 쓰지 않음. 해제·정정은 새 요청 |
| `rejected`, `cancelled`, `expired`, `invalidated`, `failed` | 종료. 이력 보존, 재신청은 새 요청 |

해제 요청의 당사자는 현재 대표 계정과 해제할 보조 계정으로 고정한다. 신청 계정이 그 두 계정 중 하나인지 확인하고 `pending_review`에서 시작한다. 본인 계정을 떼거나 대표 계정이 자신의 보조 계정을 떼는 요청만 가능하다. 상대 계정의 추가 동의는 요구하지 않는다. 해제 시 추가 동의를 요구해 상대 계정이 요청을 막지 못하게 하되, 적용에는 다른 관리자의 검토·승인이 필요하다. 원본과 과거 관측값은 그대로 남는다.

관리자 상세 조회는 영향 미리보기일 뿐 변경을 확정하지 않는다. 미리보기에는 원본 집계 변경 번호, 현재 계정 구성 버전과 요청 버전, 확인한 관리자 ID를 담는다. 승인 시 모두 일치해야 한다. 사이에 새 인증·삭제·계정 구성이 바뀌면 `기록이 바뀌었어요. 영향을 다시 확인해 주세요.`로 새 미리보기를 요구한다. DB 변경 번호는 원본·일별 집계의 실제 내용이 바뀐 같은 트랜잭션에서 증가시키며, 동일 메시지의 변경 없는 재처리는 번호를 올리지 않는다. 미리보기와 승인 검증은 같은 잠금·일관된 DB 읽기 기준을 사용한다. 또한 단순 성공 수집 시각을 변경 감지로 대신하지 않는다.

승인 후 다음 수집까지 새 운동 기록이 추가되는 것은 정상이다. 승인 대상인 계정과 동작은 고정하고, 적용 시점의 최신 기록으로 정확히 재계산한다. 관리자는 수치를 보장하는 것이 아니라 계정 관계 변경을 승인한다. 다른 관리자 동시 승인·승인/취소 경쟁은 요청 버전과 조건부 상태 변경으로 한 번만 확정한다. 요청 생성 interaction ID를 유일 키로 보존하고, 동의·검토 동작도 interaction ID별 처리 결과를 같은 상태 변경 트랜잭션에 기록해 재전송이 새 요청이나 새 변경을 만들지 않게 한다.

## 5. 원본과 사람 식별의 분리

`workout_events.user_id`, `message_id`, `workout_logs(user_id, log_date)`는 원본 계정 기준으로 유지한다. ID 치환·이벤트 이동·기존 일별 행의 파괴적 합병을 하지 않는다. 삭제·수정과 중복 방지는 지금처럼 원본 메시지 ID로 처리한다.

아래는 `solitary_athlete` 안에 둘 논리 모델이다. 구체 SQL은 구현 계획과 마이그레이션에서 확정한다.

| 저장소 | 주요 정보와 제약 |
| --- | --- |
| `mukmuk_people` | 안정적인 `person_id` UUID, 대표 Discord ID. 대표 이름 변경으로 person ID가 달라지지 않음 |
| `mukmuk_person_accounts` | 서버·원본 Discord ID, person ID, 유효 시작/종료 집계 버전. 같은 버전에서 한 계정은 한 사람에만 소속 |
| `mukmuk_account_link_requests` | 요청 ID, 연결/해제, 당사자·대상 그룹, 동의·만료·검토·적용 시각, 처리자, 상태·내용/상태 버전·승인 근거, 선점 임대·시도 번호·재시도 시각·오류 코드 |
| `mukmuk_account_link_actions` | 동작 interaction ID 유일 키, 요청·호출자·동작·처리 결과. 중복 실행 방지와 비공개 처리 이력 |
| `mukmuk_identity_state` | 현재 공개 집계 버전, 원본 집계 변경 번호. 승인 대기와 공개 상태를 구분 |
| `mukmuk_identity_changes` | 적용된 변경 버전, 요청·처리자, 변경 전후 소속, 적용 시각. 추후 차트의 변경 지점 근거 |

기존 기록 계정에는 1계정=1사람으로 식별자를 준비한다. 이 최초 준비는 수치가 바뀌지 않는 버전 0이다. 새 계정의 첫 인증도 독립된 사람으로 등록하며, 일반적인 신규 참여만으로 연결 기준 버전을 올리거나 전일 비교를 숨기지 않는다. 기록 없는 신청 대상은 준비할 수 있지만 기록 기반 roster·분모에서는 제외한다.

연결 시 대상 계정을 대표 계정의 person ID로 옮기고 기존 사람 행은 보존한다. 해제 시 그 계정의 기존 독립 person ID로 복귀한다. 소속의 유효 기간을 보존해 이전 연결 버전도 해석할 수 있게 한다. 대표 계정이 탈퇴해도 자동 해제·대표 교체·기록 삭제를 하지 않는다. 마지막 알려진 대표 이름을 사용하고 운영 검토 대상으로 남긴다.

## 6. 한 사람·하루 한 칸과 통계 수식

공개 조회용 논리 집계 `person_day(revision, person_id, log_date)`를 서버에서 만든다. 해당 버전의 소속에 따라 같은 사람·같은 KST 날짜의 원본들을 모은다. Python·Edge·웹이 따로 연결 관계를 추측하거나 브라우저만 합치지 않는다.

- 운동일: 원본 계정 수·메시지 수에 관계없이 1일.
- 사진: 모든 원본의 `has_photo` OR. 마지막 사진 삭제 시 남은 원본으로 다시 판단.
- 메모: 원본 메시지 작성 시각·메시지 ID 순으로 보존. 같은 문구라는 이유로 서로 다른 메시지를 삭제하지 않음.
- 인증 횟수: 원본 메시지 개수. 운동일수로 사용하지 않음.
- 표시명: 대표 계정의 마지막 확인된 이름. 부계정의 최근 인증 이름이 대표 이름을 덮어쓰지 않음.
- 개인 주간·연속·누적, 웹 연간 잔디, 월간 KPI 5종, 운동왕 동률, Discord 현황판 모두 같은 person_day를 사용.

월간 수집 집계는 다음과 같다. 선택 연도와 독립된 현재 KST 월이라는 기존 원칙을 유지한다.

```text
N = 해당 월에 인증이 있는 서로 다른 person_id 수
S = 해당 월 시작일부터 수집 기준일까지의 (person_id, log_date) 수
D = 마지막 성공 수집일의 KST 월 경과 일수
함께 심은 잔디 = N > 0 이면 100 × S / (N × D), 아니면 0%
```

연간 전체 잔디는 선택 연도의 날짜별 person_id 수를 분자로 쓴다. 분모는 기존 구현대로 **전체 인증 이력이 있는 person_id 수**이며 특정 월이나 선택 연도로 제한하지 않는다. 기존 `min(인원, 50)` 농도 규칙을 유지한다. 연결 신청·승인이나 서버 재가입만으로 분모를 늘리지 않는다. 개인 잔디의 사진 2단계도 유지한다.

가상 예: 월 경과 10일, 계정 A의 인증일 3일, B의 인증일 2일, 그중 겹친 날 1일이면 연결 전 `N=2, S=5, 25%`, 연결 후 `N=1, S=4, 40%`다. 이 15%p를 신규 운동으로 인한 증가로 보여주지 않는다. B의 기록이 없다면 연결 전후 N·S·비율은 같다.

원본 갱신은 계속 명시적 `/기록갱신`만 사용한다. 일반 멤버가 연결된 다른 계정을 지정했다는 이유로 원본 수정·삭제 재검증 권한을 얻지 않는다. 본인 원본 ID만 갱신하고, 타 계정은 해당 계정에서 호출하거나 기존 관리자 권한을 사용한다. 연결 해제 후에도 원본의 작성자·삭제 근거가 바뀌지 않는다.

## 7. 과거 관측 보존과 증감 비교

월간 현재/이전 표본 각각과 일별 관측 행에 비식별 `identity_revision`을 추가한다. 기존 표본은 0을 붙이며 날짜·수집 시각·N·S·D를 바꾸지 않는다. 향후 집계 수식 자체가 달라지는 경우를 구분할 `calculation_version`도 표본에 둔다. 이번 사람 단위 계산의 최초 버전은 1이며, 기존 1계정=1사람 표본도 같은 수식으로 해석 가능하다. 개인 ID·연결 관계는 익명 집계 표본에 넣지 않는다.

연결·해제가 실제 적용되면 서버 전체 `identity_revision`을 증가시킨다. 새 버전의 소속과 그 버전에서 계산한 N·S·D, 공개 성공 시각, 요청 완료·변경 이력을 한 트랜잭션으로 게시한다. 승인만으로 버전이나 수치를 바꾸지 않는다.

전일 대비는 **같은 KST 월의 정확한 전날 표본이 있고, 두 표본의 identity_revision과 calculation_version이 모두 같을 때만** 기존 수식으로 계산한다. 버전이 다르면 숫자·화살표·변동 없음을 표시하지 않고 `계정 변경으로 비교 제외`로 표시한다. 다음 날에도 정확한 전날 표본·같은 버전 조건이 충족되어야 비교를 재개한다. 수집 공백·월초는 기존처럼 비교 기록 없음이다. 수치가 우연히 같아도 기준 버전이 다르면 비교하지 않는다.

지나간 날짜의 일별 관측값은 재작성하지 않는다. 현재 날짜는 기존 정책대로 마지막 성공 집계로 갱신하므로, 같은 날 변경 전 관측 행이 변경 후 값으로 대체될 수 있다. 하루 중 계정 변경이 있었다는 사실은 별도 변경 이력에 남는다. 없는 날짜·당시 알 수 없던 사람 단위 과거 집계는 만들지 않는다.

연결 후 과거 연도의 잔디를 조회하면 **현재 소속으로 다시 모은 기록**을 표시한다. 반면 일별 이력은 **당시 관측한 집계**다. 둘은 목적이 다르며, 향후 차트는 서로 다른 버전 사이 선·증감 비교를 끊고 변경 지점을 표시해야 한다. 이번 범위에 차트 화면·조회 API는 포함하지 않는다.

## 8. 적용 트랜잭션·동시성·실패

신청·동의·승인은 기존 Edge 수신기에서 처리하고, 승인된 연결의 공개 적용은 기존 수집기의 성공 확정 경로에서 수행한다. 새 상시 프로세스·컨테이너·Cron은 추가하지 않는다. 맥북이 쉬면 반영도 대기하며 일일 보완 수집도 같은 경로를 사용한다.

적용 순서:

1. 승인된 요청을 오래 대기한 순서로 실행당 최대 1건 조건부 선점하고 현재 당사자·관리자 자격을 조회한다. 이 작업의 HTTP·DB 처리는 실행당 30초 이내이며 수집기 전체 240초 제한을 유지한다. HTTP 조회를 DB 집계 잠금 안에서 기다리지 않는다.
2. 기존 `mukmuk-workouts` advisory lock 아래 동일/역행 수집 시각을 먼저 거부한 뒤 요청·현재 구성 버전과 재검증 결과의 신선도를 확인한다. 이번 확정에 사용할 KST 수집 기준일은 HTTP 확인을 마친 뒤 하나의 성공 시각에서 도출한다. REST 확인은 같은 실행에서 적용 직전 완료된 결과만 사용한다. Discord와 DB의 분산 트랜잭션은 불가능하므로 이 짧은 시간 사이의 권한 변경까지 원자적으로 보장한다고 표현하지 않는다.
3. 원본 집계에 새 소속을 적용해 사람 단위 person_day를 구성한다. 현재 월·전체 분모·개인 조회가 모두 같은 소속 버전을 사용하게 한다.
4. 소속 버전, 월간 현재/이전 표본, 당일 관측, 수집 상태·성공 시각, 요청 `applied`, 변경 이력을 같은 트랜잭션으로 확정한다. 어느 한 저장이 실패하면 모두 롤백한다.
5. 확정된 버전으로 Discord 현황판을 갱신한다. Discord HTTP 게시와 DB 커밋의 원자성은 보장하지 않는다. 현황판 실패는 별도 운영 오류로 남기고 다음 수집에서 재시도하며 DB의 적용을 되돌리지 않는다.

현재 `run_sync`는 현황판 게시 뒤 `Store.success`를 호출한다. 구현 시 이 순서를 조정해야 하며, 승인된 구성을 현황판에 먼저 게시한 뒤 DB 적용이 실패하는 경로를 남기지 않는다. 공개 마지막 성공 시각은 데이터 확정 시각임을 명확히 하고, 현황판 게시 실패를 숨기지 않는다.

선점 임대와 시도 번호를 DB에서 다시 확인하고, 오래된 실행은 요청 상태·소속·집계를 확정하지 못하게 한다. 같은 요청 재실행·동일/역행 수집 시각으로 버전을 두 번 올리거나 과거 일별 관측을 쓰지 않는다. 겹치는 그룹의 변경은 직렬화하고, 승인 이후 소속이 바뀐 요청은 자동 재해석하지 않고 `invalidated`로 종료한다. 429는 retry_after까지 보류하고 실패 횟수에 넣지 않는다. 타임아웃·5xx·DB 저장 오류는 롤백 후 오류·재시도 시각만 별도 트랜잭션에 기록한다. 일시 오류가 10회 연속 이어지면 `failed`로 종료해 계속 대기 중인 요청이 계정을 무기한 점유하지 않게 한다. 새 요청은 동의·승인을 다시 받는다. 실패 기록은 관리자 목록과 당사자 현황에서 조회하며, 처리 실패를 적용 완료로 표시하지 않는다.

## 9. 웹·슬래시·사진 API 경계

`person_id`와 Discord `user_id`를 다른 필드로 취급한다. UUID를 기존 숫자 ID 필드에 억지로 넣거나 대표 ID로 원본 작성자를 덮어쓰지 않는다. 새 버전의 멤버·연간 로그·개인 통계 RPC는 person_id, 대표 표시명과 공개 집계 버전을 반환한다. 원본 계정 전체 목록·동의·승인 이력은 공개하지 않는다.

웹은 처음 얻은 공개 identity_revision을 이후 roster·연간 페이지·현재 월·이전 연도 스트릭 연장·참여율 조회에 명시한다. RPC는 요청한 버전과 현재 공개 버전이 다르면 전용 오류로 거부한다. 하나라도 기준 변경 오류가 나면 그 로드의 결과 전체를 버리고 처음부터 다시 읽는다. 자동 재시도는 2회까지이며 계속 바뀌면 기존 화면을 보존하고 새로고침 안내를 표시한다. 기준 변경을 코드 만료나 빈 기록으로 표시하지 않는다.

배포는 먼저 새 버전 RPC·웹·Edge·Python을 1계정=1사람 상태로 준비하고 기존 결과와 일치하는지 확인한 뒤, 기능 플래그로 신규 요청·적용을 활성화한다. 기존 RPC를 같은 이름으로 사람 단위 응답으로 바꾸지 않는다. 최초 실제 계정 변경부터 구버전 웹의 기존 roster·연간 로그·참여율 RPC와 사진 요청은 HTTP 409 `client_update_required`로 함께 거부해 새로고침이 필요하게 한다. 월간 코드 만료로 분류되는 400/401/403을 이 용도로 사용하지 않는다. 구버전 요청에 새 사람 단위 표본만 반환하는 경로를 남기지 않는다.

이미 열려 있던 구버전 화면의 완성된 과거 조회 결과는 새로고침 전까지 남을 수 있다. 그 화면에 서버가 새 계산 결과를 일부만 끼워 넣지는 않는다. 새 웹에서는 해당 오류를 명확한 새로고침 안내로 처리한다. 실서비스 활성화 전 구버전 번들을 이용해 부분 조회·페이지네이션·사진 요청이 섞이지 않는지도 검증한다.

`/잔디`는 지정된 실제 계정 ID에서 현재 person_id를 찾아 연결된 날짜를 조회한다. 결과는 지금처럼 공개·300초 삭제이며 내부 연결 계정 목록은 노출하지 않는다. `/기록갱신`의 원본 권한 범위는 6절을 따른다.

사진은 person_id·날짜와 집계 버전으로 요청하고, 서버가 그 사람에 속한 원본 이벤트를 페이지 조회한다. 이벤트마다 원본 `user_id`를 함께 읽어 Discord 응답의 `author.id`와 대조한다. 대표 계정 ID와 비교하면 부계정 사진이 잘못 차단되므로 기존 검사 그대로 재사용할 수 없다. 월간 코드 검증·서버/채널 검증·메시지 단위 페이지네이션·지연 로딩·원본 링크·서명 URL 캐시 정책은 유지한다. 소속이 바뀌면 진행 중 응답과 클라이언트 사진 캐시를 폐기하고 다시 조회한다. 이미 전달된 Discord URL이나 브라우저 캐시의 즉시 회수까지 보장하지 않는다.

## 10. 접근 제어와 운영 범위

새 원본 연결·요청·감사 테이블은 서버 전용 RLS와 명시적 최소 권한을 적용한다. PUBLIC·anon·authenticated·service_role의 직접 읽기/쓰기를 허용하지 않는다. 기존 앱 전용 역할과 묵묵 스키마 경계를 유지한다. 웹은 유효한 월간 코드 검증 후 공개용 집계 RPC만 호출하며, 코드 보유가 계정 연결 승인 권한을 뜻하지 않는다.

모든 Discord 게시에는 `allowed_mentions: { parse: [] }`를 지정한다. 요청 ID·상태·비식별 오류 코드로 운영을 관측하고 실제 계정 ID·원문·사진·토큰을 로그·공개 문서·테스트에 남기지 않는다. 처리자·소속 변경 등 필요한 감사 정보는 서버 전용 DB에 보관한다. 기능 비활성화는 신규 변경 접수·적용을 멈출 뿐 이미 적용된 소속과 통계를 몰래 raw ID 기준으로 되돌리지 않는다. 잘못된 연결은 감사 이력을 남기는 해제로 정정한다.

SQL 변경은 모두 `supabase/migrations/`에 남긴다. Python 수집기 변경 배포 시 검증한 launchd 런타임도 갱신한다. 공유 Supabase의 다른 앱·전역 권한·키는 변경하지 않는다. Discord 명령 등록·실계정 신청·승인은 구현과 검증 후 별도 배포 단계에서 수행한다.

## 11. 구현 전 수용 기준

| 실패 조건 또는 사례 | 기대 결과 |
| --- | --- |
| 닉네임만 변경 | 같은 사람·같은 기록, 계정 연결 요청 불필요 |
| 기록 없는 부계정 연결 | 인원·칸 수 불변, 향후 첫 인증부터 기존 사람으로 반영 |
| 두 계정 같은 날 텍스트/사진 인증 | 한 칸·사진 단계, 원본과 메모 모두 보존 |
| 다른 날짜 인증·연도 경계·스트릭 연결 | 날짜 합집합으로 주간·연속·누적·운동왕 일치 |
| 마지막 사진 제거·메시지 삭제 | 남은 원본으로 재집계, 하루 중복 가산 없음 |
| 월간 인원과 전체 잔디 분모 | 월간은 해당 월 인증 사람, 전체는 전체 인증 이력 사람 |
| 관리자 자신의 계정 또는 이미 연결된 계정으로 자기 승인 | 거부, 다른 관리자 검토 필요 |
| 두 계정 동의 전 관리자 승인 | 거부, 소속·통계 불변 |
| 위조 버튼·다른 계정·다른 서버·DM | 요청·동의·검토·상태 조회 모두 권한 검사 |
| 권한 상실·대상 탈퇴·구성 변경 | 원본 보존, 적용 보류 또는 invalidated, 임의 합병 없음 |
| HTTP 오류·수집기 중단 | 승인 대기 유지, 실패를 적용 완료로 표시하지 않음 |
| 승인 미리보기 후 원본 변경 | 다시 확인 요구; 오래된 예상 수치로 승인하지 않음 |
| 재전송·동시 승인/취소·중복 수집 | 요청·소속 버전·이력은 한 번만 확정 |
| 당일 연결·해제 여러 번 | 각 변경 버전 증가, 현재 값 정확, 과거 일별 값 보존 |
| 전날과 계정 기준이 다름 | 전일 증감 없음, 비교 제외 사유 표시 |
| 다음 날 동일 기준·정확한 전날 표본 존재 | 전일 대비 재개, 이전 기준 표본으로 보정하지 않음 |
| 월초·윤일·수집 공백 | KST 경계·기존 비교 없음 규칙 유지 |
| 저장 중 오류 주입 | 소속·표본·일별 이력·성공 시각·요청 상태 모두 롤백 |
| 구버전 웹으로 첫 계정 변경 전후 조회 | 변경 후 기존 필수·참여율·사진 경로 모두 갱신 필요 응답, 계산 기준 혼합 없음 |
| 웹 페이지·사진 로딩 중 버전 변경 | 섞인 결과 폐기·재조회, 사진 원본 작성자 검사 유지 |
| DB 반영 후 현황판 HTTP 실패 | DB 완료 유지·게시 오류 관측·다음 수집 재시도 |
| 익명 직접 조회·공유 코드로 승인 시도 | 연결 원본·요청·감사 접근과 변경 모두 거부 |

Python·Edge·웹에 같은 가상 날짜·계정 사례를 사용해 결과를 대조한다. DB 트랜잭션·권한·페이지네이션 검증, 서명된 명령/버튼 검증, 타입 검사·정적 빌드·브라우저 검증을 포함한다. 이 문서 단계에서 구현 테스트나 실서비스 승인을 수행한 것으로 기록하지 않는다.
